- 日期：2026-11-09

## 1. 目标与确认结论

在现有超级工作台工程内新增独立的“抖音运营”应用，复用统一登录和部署体系，支持同一工作台用户管理多个获授权的抖音账号，完成以下短视频运营闭环：

**选题发现 → 参考内容采集 → AI辅助原创脚本创作 → 外部人工制作视频 → 成片上传 → 人工审核 → 系统发布／定时发布 → 真实数据回收 → 复盘记录。**

已确认的产品决策：

1. 目标是完整运营闭环，而非单独提供爬虫入口。
2. 核心内容形态为短视频。
3. 视频由人工在外部制作；系统提供AI辅助创作，不建设自动成片系统。
4. 发布必须经过人工审核，并由系统执行，不以人工发布后回填代替。
5. 首期支持多个抖音账号，但不包含一键群发。
6. 同一人审核并发布；首期不新增团队、角色权限或多级审批。
7. 在同一工程内增加独立抖音应用，不把小红书页面改造成通用多平台页面。
8. 保持现有小红书业务、数据范围、路由与调度行为不变。

“完整闭环”是最终验收目标，允许分阶段实施，但不得将采集完成、页面齐全或模拟发布视为闭环完成。

先开展小范围技术验证，再进入完整业务实现：

| 定时执行 | 工作台调度所需条件、授权有效性、到期执行和取消方式 | 不要求上游提供原生定时接口，可由工作台按审核后的计划执行 |
| 指标回收 | 指标字段、权限范围、更新时间或延迟、作品关联和真实响应 | 至少能回收一种真实互动指标；否则暂停并重新确认闭环目标 |
| 使用成本与限制 | 平台权限、费用、配额、运行环境和维护依赖 | 在实施前说明，不隐含免费或永久可用承诺 |

验证结论必须说明哪些能力可用、哪些不可用、哪些未验证。发布失败或无法回收真实指标时，不擅自降级为人工发布、模拟数据或仅展示页面。

真实平台发布需要用户对目标账号、具体成片和发布时间的明确授权。确认本需求文档不等于授权执行真实发布。

## 4. 方案比较与选择

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 同工程内新增独立抖音应用 | 复用认证与部署；业务边界清晰；有利于保护小红书功能 | 需新增抖音适配层及业务模块 | 已选定 |
| 将小红书页面扩展成多平台通用页面 | 可复用部分界面 | 扩大既有业务改造面，平台差异容易渗透原模块 | 不采用 |
| 独立部署抖音系统，由工作台提供入口 | 隔离充分 | 增加认证、部署、文件和任务协同成本 | 不采用 |

核心原则：**共享基础设施，不混用平台业务逻辑。**

## 5. 应用与模块架构

### 5.1 入口与页面

- 在现有应用目录中新增“抖音运营”，应用标识为 `douyin`。
- 通过 `/apps/douyin` 解析至 `/platforms/douyin/dashboard`。
- 抖音页面使用自己的工作区菜单与路由，不嵌入小红书固定菜单。
- 支持返回应用中心，沿用现有登录守卫、退出行为和主题体系。
- 应用目录与后端社交平台注册分别维护，不通过简单开启占位项冒充业务接入完成。
- 仅当获批准的首期能力实际可用后，才将应用作为可用入口交付，不以空页面或模拟数据充当完成。

建议页面分组：总览、账号管理、选题与参考库、创作工坊、成片管理、审核与发布、作品与复盘、任务记录。总览仅汇总本用户抖音业务，不扩展为跨应用统计平台。

### 5.2 调用边界

调用关系：

**抖音页面 → 抖音API → 抖音业务服务 → 采集／发布／指标适配层 → 外部平台。**

| 单元 | 职责 | 接口与依赖边界 |
| --- | --- | --- |
| 应用注册与工作区 | 应用入口、导航和布局 | 使用现有认证与应用注册，不获取平台凭证 |
| 账号服务 | 账号身份、凭证、授权状态和归属 | 提供经过归属校验的账号引用，凭证只在服务端解密使用 |
| 参考内容服务 | 来源采集、规范化、标签及备注 | 通过采集适配层调用上游，不直接依赖上游响应结构 |
| 创作服务 | 草稿、AI辅助及参考关联 | 使用现有模型配置时逐项验证权限与兼容性；不改动小红书AI业务 |
| 成片服务 | 视频、封面及版本管理 | 依赖受保护的文件存储和媒体基础校验，不负责剪辑或渲染 |
| 审核与发布服务 | 审核快照、计划、执行、取消及结果确认 | 通过发布适配层执行；依赖持久化任务与幂等控制 |
| 指标与复盘服务 | 作品关联、指标快照、手工复盘结论 | 使用指标适配层，不以未获取的数据填零 |
| 任务与通知 | 执行记录、错误追踪和必要提醒 | 现有能力仅在兼容性与用户隔离验证后复用，否则增加抖音专用实现 |

上游代码通过独立依赖区域或明确命名空间接入，固定版本并保留许可证及来源记录。接入方式在技术验证后写入实施计划，不直接覆盖原项目的 `apis/`、签名脚本或依赖文件；不运行来源不明的安装脚本。

## 6. 首期功能需求

### 6.1 多账号管理

- 当前用户可以绑定和管理多个自己有权运营的抖音账号。
- 保存平台账号标识、展示信息、授权状态、最近检查时间及必要的授权元数据。
- 独立加密保存账号凭证，不因用户切换应用而共用平台凭证。
- 授权失效时提示重新授权，并阻止或暂停该账号的待发布任务。
- 一个账号不可用，不阻塞其他账号的任务。
- 同一账号的发布受队列控制，不允许同一发布任务并发执行。
- 首期不新增角色、团队或多级审批，不承诺账号在不同工作台用户之间共享。

### 6.2 选题与参考内容库

- 优先支持通过作品链接创建采集任务，能力可行性以第3节验证为准。
- 保存来源平台、规范化作品标识、原链接、可获取的作者与内容信息、采集时间和用户备注。
- 支持查看、关键词筛选、标签管理和导出允许保存的内容字段；不导出凭证或敏感原始响应。
- 同一用户重复采集同一平台作品时复用已有记录，更新可刷新字段，保留已有标签、备注和创作关联；不同用户分别拥有自己的记录。
- 关键词搜索、作者作品采集不是已确认可用功能，须经过验证与范围更新才能纳入。
- 参考作品不自动成为待发布素材；能够采集或访问不等于获得下载、改编或发布授权。

### 6.3 创作工坊与AI辅助

- 创建选题与创作草稿，可关联多条参考内容。
- AI辅助生成原创脚本、标题、描述、标签及封面文案。
- AI输出作为可编辑草稿，由用户确认，不直接触发发布。
- 用户可维护不依赖AI生成的人工草稿，AI失败不丢失已保存内容。
- AI请求只发送用户已确认用于该操作的必要内容，不包含平台凭证；发送前明确涉及外部模型服务。
- 现有模型配置的具体复用方式在实施计划中核验，不默认所有现有配置和接口可直接复用。

### 6.4 人工成片与封面管理

- 用户在外部制作视频，再上传到工作台；可上传和选择对应封面。
- 支持视频预览、基础格式和文件校验，保存文件大小、类型及可取得的时长、分辨率等元数据。
- 文件限制由验证后的目标发布方式决定；不在需求阶段虚构平台规格。
- 成片关联创作草稿，并明确当前待发布版本。
- 视频或封面替换产生新版本，不覆盖已审核版本；已有审核和历史发布记录必须仍可追溯。
- 支持清理未被审核或发布任务引用的文件；被有效任务引用的文件不得直接删除。
- 文件上传本身不构成平台发布。

### 6.5 人工审核

审核操作必须显式展示并确认以下快照：

- 目标抖音账号。
- 成片及封面版本。
- 标题、描述、标签及其他必需发布字段。
- 立即发布或定时发布方式；定时任务的计划执行时间。

同一人可以完成编辑、审核及提交，不引入分离职责或双人审批。

通过后修改视频、封面、文案、账号或发布时间，原审核失效。不得仅改变界面状态而继续沿用旧审核执行发布。留存审核人、时间、快照与失效原因。

### 6.6 系统发布与定时发布

- 仅允许有效审核对应的版本进入发布执行。
- 支持立即发布、定时发布和执行前取消。
- 定时计划的展示与用户输入按北京时间（Asia/Shanghai）解释；存储与调度遵循现有时间规范并在边界显式转换。
- 执行前再次检查审核、账号授权、文件存在性及平台要求。
- 一个发布任务仅对应一个目标账号；发布到其他账号必须创建并审核独立任务。
- 保存任务标识、作品ID、作品链接、执行时间、结果及可公开的错误信息。
- 上传完成、发布成功、平台审核状态和作品可见性分别记录；平台审核中或不可见不冒充已公开发布。
- 原生平台定时能力不是前提；工作台可按审核后的计划到期调用发布接口。
- 已过计划时间且未开始的任务，在服务恢复后不得直接补发：先标记为逾期待处理，用户调整时间后重新审核提交。已开始任务按实际执行状态恢复或对账。

### 6.7 作品数据与复盘

- 已发布作品关联目标账号、发布任务、审核快照及来源创作。
- 回收授权接口实际支持的指标，并保存采集时间和指标快照。
- 支持手动刷新；计划刷新采用保守频率并遵守接口限制，具体频率由能力验证结果写入实施计划。
- 无法获取的字段显示“不可获取”；尚未采集显示“未采集”，均不显示为零。
- 刷新失败时保留上次成功数据与采集时间，并显示失败原因。
- 支持按账号和作品查看记录，人工填写复盘结论与后续选题备注。
- 首期不承诺归因分析、收益统计或平台未提供的私有指标。

### 6.8 任务与通知

- 记录采集、上传、发布及指标刷新任务的归属、状态、阶段、时间与失败原因。
- 授权失效、发布失败、结果待确认、定时任务逾期时提供明确提示。
- 重试仅面向可安全重试的操作；发布结果不明时必须先核对，不提供直接盲重发。
- 日志仅保留必要诊断信息，不记录Cookie、Token、密钥或完整敏感响应。

## 7. 数据设计原则

新增抖音业务表，通过独立迁移管理，不修改小红书现有业务表的结构与既有行为。以下为逻辑实体，不是最终表名或迁移代码：

| 实体 | 主要内容与关联 |
| --- | --- |
| 抖音账号 | 所属工作台用户、平台账号标识、加密凭证、授权状态 |
| 选题与参考作品 | 所属用户、来源标识、采集信息、标签、备注 |
| 创作草稿 | 所属用户、脚本文案、参考关联、编辑版本 |
| 成片与封面版本 | 所属用户、草稿关联、受保护文件引用、校验元数据 |
| 审核记录 | 审核用户、目标账号、不可变发布快照、有效性与时间 |
| 发布任务 | 用户与账号、审核引用、计划时间、执行状态、幂等及对账信息 |
| 已发布作品 | 平台作品ID、账号、任务关联、链接、平台审核与可见性状态 |
| 指标快照与复盘 | 作品关联、真实指标、采集时间、人工复盘结论 |
| 任务记录 | 所属用户、业务关联、执行阶段、错误与耗时 |

完整数据链路为：

**参考内容 → 创作草稿 → 成片版本 → 审核快照 → 发布任务 → 已发布作品 → 指标与复盘。**

用户隔离适用于列表、详情、修改、任务执行、文件预览、下载和导出，不能只在前端隐藏。平台账号、文件、草稿与任务关联时，服务端必须验证它们属于当前用户。

文件复用现有存储设施不等于复用公开访问方式；抖音成片和导出文件必须受认证与归属保护，不得因放入公共静态目录而绕过权限。

## 8. 状态与异常规则

### 8.1 审核与发布状态

审核状态独立于发布执行状态：草稿／待审核、已通过、已失效。

发布任务至少区分：待执行、执行中、结果待确认、发布成功、明确失败、已取消、授权阻塞、逾期待处理。

- 失败只表示已有明确失败证据，不包含“请求超时但平台可能已发布”。
- 每次执行前核对审核快照和当前引用，审核失效不可继续执行。
- 已取消任务的执行入口必须拒绝；接口重复取消可安全返回已有结果。
- 执行中请求取消时，应依据平台能力与实际阶段返回结果；不承诺撤回已发送的发布请求或删除已发布作品。
- 平台审核、下架、可见性等作为作品状态记录，不反向抹除历史发布结果。

### 8.2 幂等与恢复

- 对同一发布意图创建和提交任务必须具备幂等保护，重复点击不生成多次发布。
- 同一任务同一时刻只允许一个执行者，任务状态与执行权必须持久化，不能仅靠进程内变量。
- 多进程调度、任务重试和服务重启不得导致同一任务重复发布。
- 请求超时或执行中断后先进入对账流程，按平台返回标识或可验证记录确认结果。
- 若接入方式无法确认不明结果，保持“结果待确认”并阻止自动重发；不能凭本地无作品ID判定未发布。
- 正常恢复尚未到期且审核有效的任务；已逾期未执行的任务按第6.6节处理。

### 8.3 异常处置表

| 情况 | 系统行为 |
| --- | --- |
| 授权失效 | 阻止该账号发布，提示重新授权；恢复后重新检查未执行任务，不自动补发逾期任务 |
| 平台限流或要求验证 | 暂停相关操作并提示，遵守冷却要求，不绕过验证 |
| 审核后修改内容或计划 | 使原审核失效，阻止原任务执行，重新审核后才可重新排队 |
| 视频或封面丢失／校验失败 | 阻止发布，提示修复成片；变更文件后重新审核 |
| 发布超时 | 进入结果待确认并对账，禁止盲目重发 |
| 平台明确拒绝 | 保存脱敏原因，允许修正；修正审核字段后必须重审 |
| 调度器停机 | 保留持久化任务；恢复后区分未到期、逾期和已执行不明任务 |
| 指标接口失败 | 保留最近成功快照，标记本次刷新失败，不覆盖为零 |
| AI服务失败 | 保留人工草稿和已有内容，允许用户继续编辑或重新请求 |
| 一个账号失败 | 隔离该账号的问题，不阻塞其他账号 |

## 9. 安全、合规与非功能要求

1. 仅接入用户有权访问和运营的账号与内容，核验开源许可、平台条款及素材使用权。

3. 参考视频默认用于研究，不自动下载改写后搬运发布；访问权限不等于内容版权。
4. 凭证与模型密钥在服务端加密保存，最小范围解密，不进入日志、导出、前端响应或AI上下文。
5. 只采集业务必要字段；首期不包含评论用户数据采集等额外个人信息处理。
6. 所有外部操作设置超时和受控重试；并发、配额和刷新频率依据验证结果限制，不设置虚构吞吐承诺。
7. 耗时操作通过可追踪任务执行，页面可刷新后继续查询状态，不依赖浏览器长连接存活才能完成发布。
8. 上传文件采用生成的存储标识，检查类型、大小与路径安全；文件名不得控制服务器路径，不执行上传内容。
9. 媒体采集或链接解析必须校验来源与重定向，禁止访问内网、回环、元数据服务和非预期协议，防止SSRF。
10. 数据导出不得包含凭证，CSV等表格导出应处理公式注入风险。
11. 对用户展示可理解的错误，对任务保留可关联的脱敏诊断记录；不能把平台错误伪装成成功。
12. 不为本需求顺带重构或修复无关小红书业务；阻断问题单独记录并向用户说明。

## 12. 验收标准

### 12.1 能力门槛

- 许可证、固定版本、依赖、平台权限、使用限制与成本有记录。
- 使用获授权测试账号证明作品链接采集、系统发布、结果确认及至少一种真实互动指标可用；若不能满足，按第3节处理，不宣告闭环可交付。
- 采集和发布凭证及适配方式明确，不把未经验证的能力列为已实现。

### 12.2 核心真实闭环

经用户对测试内容与账号明确授权后，至少一条人工成片完成：

1. 关联选题及参考内容。
2. 使用AI辅助生成并人工编辑创作文案。
3. 上传成片和封面并通过校验。
4. 确认目标账号与发布快照，完成审核。
5. 系统执行发布并确认真实作品ID和链接。
6. 分别呈现发布、平台审核与可见性状态。
7. 回收至少一种真实互动指标，记录指标采集时间。
8. 保存人工复盘结论，可追溯到创作和发布任务。

模拟数据、上传成功、仅返回任务ID或页面展示均不能替代真实发布证据。

### 12.3 多账号与隔离

- 至少两个获授权抖音账号可分别管理、创建任务并关联作品记录。
- 一个账号授权或发布失败，不阻塞另一个账号。
- 目标账号不可在审核通过后无审核地替换。
- 不同工作台用户不能查看、下载、修改或执行彼此的账号、文件、草稿、任务与导出。
- 多账号功能不以向所有账号发布同一内容作为验收方式；真实发布逐次取得授权。

### 12.4 发布与调度

- 未审核、审核失效、凭证失效、文件失效时均不可发布。
- 修改审核字段会使原审核失效；已排队任务不能使用旧快照执行新内容。
- 重复点击、并发调度、可重试错误、超时和进程重启不导致同一任务重复发布。
- 请求超时进入结果待确认，对账前不自动重发。
- 定时发布按北京时间正确执行，执行前取消后不再开始。
- 取消与执行竞争时返回真实阶段，不误报已取消已执行的平台请求。
- 停机后逾期未执行任务不自动补发，调整时间后重新审核。
- 明确记录平台拒绝、审核中及不可见等状态，不混为公开发布成功。

### 12.5 数据与AI

- 同用户重复采集同一来源作品不产生重复参考记录，不丢失标签、备注和创作关联。
- 新成片版本不覆盖已审核引用，历史记录可追溯。
- AI失败不清空草稿；未确认的AI输出不能直接发布。
- 指标不可获取、尚未采集、成功为零、刷新失败能明确区分。
- 刷新失败后仍能查看最近成功指标及其时间。
- 日志、响应、导出和AI请求不泄露平台凭证。

### 12.6 小红书兼容性

- 原有小红书路由、页面、账号、采集、创作、发布和调度行为不变。
- 不改动小红书业务表结构及既有数据范围。
- 共享基础设施调整必须有兼容性测试，不能通过改变小红书行为来适配抖音。
- 原有任务、通知、模型配置与设置不因抖音接入而混入其他用户数据或被重新定义。
